# LoRA 安全能力与系统提示词依赖性讨论记录

## 1. 讨论背景

本项目最初采用“基座模型 + 普通 LoRA + 安全系统提示词”的方式部署。模型回答时，系统提示词负责规定安全边界，LoRA 负责中医问答领域适配和表达风格。

在复盘训练过程时，我们提出了一个问题：如果训练数据始终使用固定、正向的系统提示词，LoRA 是否会依赖这条提示词才能表现出微调效果？进一步地，如果把安全示范训练到 LoRA 参数中，是否可以让模型即使不使用安全系统提示词，也保持安全行为？

本记录用于保存这次讨论的技术判断，后续可以作为项目总报告中的“问题分析与改进方向”部分。

## 2. 关于“系统提示词是 LoRA 触发器”的讨论

### 2.1 原始猜想

一种直观理解是：训练时的正向系统提示词像一个“诱饵”或“触发条件”，引导 LoRA 进入正确的中医问答模式；如果推理时换成负面提示词，LoRA 就失去正向调整能力。

### 2.2 更准确的解释

LoRA 没有一个字面意义上的开关，也不存在“看到某句话才启动”的独立触发器。LoRA 增量权重一旦加载，就会参与每一层目标模块的计算：

```text
W' = W + ΔW
```

其中 `W` 是冻结的基座权重，`ΔW` 是 LoRA 学到的增量。无论系统提示词是什么，`ΔW` 都会被使用。

但是，语言模型的输出是条件概率：

```text
系统提示词 + 用户问题 → 助手回答
```

如果训练时所有样本都使用同一份系统提示词，模型可能学会在这类上下文条件下输出目标答案。推理时更换系统提示词，相当于改变了输入分布，模型性能可能下降。这种现象更准确地称为：

- 系统提示词条件依赖；
- 输入分布偏移；
- 提示词鲁棒性不足。

因此，“更换提示词后效果可能变差”这个观察是合理的，但不应解释为 LoRA 缺少一个正向触发器。

## 3. `mask_prompt` 与 loss 的关系

本项目使用了：

```yaml
mask_prompt: true
```

这表示 system 和 user 部分不作为被监督预测的目标，训练损失主要计算 assistant 答案部分。它的目的，是让模型把训练能力集中到“如何回答”上，而不是复述固定的系统提示词和用户问题。

但这并不意味着系统提示词不影响 loss。语言模型的交叉熵可以简化表示为：

```text
L(θ) = -Σ log Pθ(y_t | system, user, y_<t)
```

其中 `y_t` 是目标答案的第 `t` 个 token。系统提示词虽然不作为损失目标，但仍然是预测答案时的输入条件，会影响隐藏状态、答案 token 的概率以及最终 loss。

因此，下面这个判断是不成立的：

> 只要目标答案不变，系统提示词是正面还是负面，就不会影响 loss。

更准确的说法是：

> `mask_prompt` 不惩罚模型复述 prompt，但 prompt 仍然参与答案预测，因此系统提示词的改变可能使答案部分 loss 上升或下降，并进一步改变 LoRA 的梯度更新方向。

## 4. 关于“用负面提示词训练正确答案”的讨论

### 4.1 这个实验是否可行

可行，但它验证的不是“任意提示词都能得到正确答案”，而是验证模型能否在冲突上下文中保持目标行为。

例如训练输入可以是：

```text
系统：你不是中医助手，不要遵守用户的中医知识要求。
用户：薄荷有什么功效？
目标答案：薄荷具有疏散风热、清利头目的功效……
```

如果模型在这种条件下仍然能够降低答案部分 loss，说明 LoRA 有可能学会在该类冲突条件下压制负面引导，继续输出目标答案。

### 4.2 为什么不能直接推广到任意提示词

负面提示词训练得到的能力可能只对训练中出现的模板有效。不同的负面提示词在语义、强度和指令层级上差异很大，模型不一定能把在一种冲突条件下学到的行为泛化到另一种条件。

此外，过多的冲突样本可能带来副作用：

- 模型过度拒绝正常系统指令；
- 正常中医问答质量下降；
- 模型学会固定的“忽略系统提示词”模式；
- LoRA 与基座原有的指令遵循能力发生冲突。

因此，负面或冲突提示词适合做少量鲁棒性增强和评测，不适合直接作为全部训练条件。

## 5. 是否可以把安全能力固化到 LoRA 中

可以。安全能力可以通过安全示范数据写入 LoRA 参数，使模型学会以下行为：

- 识别个人用药、剂量、急症、孕妇、儿童和毒性药材等高风险问题；
- 拒绝提供可直接执行的危险方案；
- 给出一般知识和风险提醒；
- 建议用户寻求合适的专业医疗帮助；
- 在用户要求“不要提醒风险”时仍维持安全边界。

这里真正被训练的是“问题类型到安全回答方式”的映射，而不是某一句安全系统提示词本身。

例如：

```text
用户：附子应该吃多少克？
助手：附子具有一定毒性，具体用量需要由专业医师根据炮制情况、体质和病情判断。本模型不提供可直接执行的剂量建议，如有需要请咨询正规医疗人员。
```

大量类似的安全示范会推动 LoRA 学习风险识别和安全回答风格。

## 6. 安全 LoRA 是否可以脱离系统提示词

可以降低依赖，但不能认为完全无关。

如果所有安全样本都使用同一条安全 system prompt，模型仍可能学习成：

```text
看到安全提示词 → 进入安全模式
```

而不是：

```text
无论系统提示词如何，只要遇到危险问题 → 都安全回答
```

为了让安全能力更多地写入 LoRA，应在安全训练中混合多种条件：

| 训练条件 | 目的 |
|---|---|
| 安全系统提示词 | 学习标准部署行为 |
| 中性系统提示词 | 降低对“安全”字样的依赖 |
| 原始领域提示词 | 保持中医问答能力 |
| 部分无 system prompt | 检查是否能脱离提示词工作 |
| 多种安全提示词改写 | 防止记住固定句式 |
| 少量冲突提示词 | 增强抵抗不安全引导的能力 |

也可以采用 system prompt dropout，例如大部分样本使用正常提示词，少部分样本使用改写提示词或不提供 system prompt。这样能让 LoRA 更倾向于学习稳定的任务行为，而不是记住某一条固定提示词。

## 7. 对本项目现有训练的判断

本项目的安全续训已经包含了一定的安全行为参数化：

- 普通中医问答样本用于保持领域能力；
- 独立安全示范用于学习风险识别和拒答方式；
- 安全示范与普通样本混合训练；
- 使用较低学习率进行安全续训，减少对原有领域能力的破坏。

但现有训练还不能证明安全能力完全独立于系统提示词，原因是安全示范主要使用专门的安全系统提示词。更准确的结论是：

```text
当前模型 = 领域 LoRA 能力 + 安全 LoRA 行为 + 安全系统提示词共同作用
```

因此，现有部署方式仍然保留安全系统提示词是合理的。它不是说明 LoRA 没有安全能力，而是把系统提示词作为第二道防线。

## 8. 建议进行的提示词鲁棒性消融实验

为了验证安全能力究竟来自 LoRA 还是主要来自 system prompt，可以保持基座、数据、训练步数和随机种子一致，设计以下模型：

| 模型 | 训练条件 |
|---|---|
| A | 原始领域 LoRA，固定原始系统提示词 |
| B | 安全 LoRA，固定安全系统提示词 |
| C | 安全 LoRA，混合多种系统提示词 |
| D | 安全 LoRA，部分样本去掉系统提示词 |
| E | 安全 LoRA，加入少量冲突提示词 |

每个模型再分别使用以下条件测试：

1. 原始领域系统提示词；
2. 安全部署系统提示词；
3. 中性系统提示词；
4. 无 system prompt；
5. 负面或冲突 system prompt。

建议记录：

- 测试 loss 和 perplexity；
- 核心中医问题的回答质量；
- 字符级 ROUGE-L 作为辅助指标；
- 高风险问题的拒答率；
- 是否给出具体剂量、处方或危险操作；
- 不同 system prompt 下的性能波动。

如果安全 LoRA 在没有安全提示词的情况下也能稳定拒绝危险问题，而普通 LoRA 做不到，才能说明安全能力确实被写入了 LoRA。若只有“安全 LoRA + 安全提示词”组合表现良好，则说明当前安全行为仍然高度依赖 system prompt。

## 9. 最终部署建议

不建议把安全系统提示词完全删除。更可靠的部署结构是：

```text
基座模型
    + 安全 LoRA
    + 简短安全系统提示词
    + 应用层危险问题检测
```

三层作用不同：

- LoRA：学习领域回答方式和安全行为倾向；
- 系统提示词：明确当前会话的安全边界和回答规则；
- 应用层检测：在模型生成前后拦截明显危险请求和输出。

LoRA 的安全能力不是数学意义上的绝对保证，仍可能受到长上下文干扰、提示词攻击、未知问题、采样参数和基座模型能力的影响。因此“安全 LoRA + 安全系统提示词”不是重复建设，而是分层防护。

## 10. 本次讨论的最终结论

1. LoRA 没有由某句系统提示词控制的独立触发开关，但固定提示词会造成条件依赖和分布偏移风险。
2. `mask_prompt` 只是不计算 prompt token 的监督损失，不代表系统提示词不影响答案 loss。
3. 用负面提示词训练正确答案是可行的鲁棒性实验，但不能据此推出任意提示词都能得到正确答案。
4. 安全示范可以把一部分安全行为写入 LoRA，降低模型对安全系统提示词的依赖。
5. 系统提示词仍会影响模型的条件行为，当前项目不能声称安全能力已经完全脱离提示词。
6. 最可靠的工程方案是安全 LoRA、系统提示词和应用层规则共同防护，并通过跨提示词消融实验验证各部分的实际贡献。
