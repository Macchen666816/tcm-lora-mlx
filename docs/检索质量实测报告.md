# RAG 检索质量实测报告：一次真实的失败定位与修复

> 场景：向 RAG 微服务新录入《薄荷的性味归经与主要功效》文档后，用「薄荷能治什么？」检索，
> **命中的却是山茱萸、裸柱菊等无关文档，新文档排名第 13**。
> 本文记录定位过程、实验对比与最终采用的方案。所有数据由 `scripts/eval_retrieval.py`
> 与 `scripts/tune_retrieval.py` 实测产出，可复现。
>
> **注**：本报告的实验在当时的 99 条知识库上进行；此后知识库已升级为
> 三立场数据集（`data_rag_stance/`，1500 条，见 `docs/三立场消融实验设计.md`）。
> 结论（需要混合检索、需给词汇路加权）与配置值沿用至今，复现脚本请把查询换成当前库中的文档。

---

## 1. 现象

| 查询 | 期望命中 | 实测排名（原始方案） |
|---|---|---|
| 薄荷能治什么？ | 薄荷的性味归经与主要功效 | **第 13 名** |
| 薄荷的性味归经与主要功效（与标题逐字相同） | 同上 | **第 37 名** |
| 孕妇用药有哪些禁忌？ | 孕期用药相关文档 | 第 1 名 ✅ |

一个与文档标题**逐字相同**的查询排到第 37 名，说明问题不在业务代码，而在检索打分本身。

## 2. 根因定位

排除项（已逐一验证）：

- ❌ 数据未入库：MySQL 与接口返回均为 99 条，新文档正文完整无乱码；
- ❌ 向量缺失/错位：`VectorStore` 自检 文档 99 / 向量 99，FAISS 命中正常；
- ❌ 索引未重建：录入后 `indexed_documents` 从 98 → 99，重建耗时 3.1 s。

真正原因在**嵌入模型的相似度尺度**。受控实验（同一模型、同一进程）：

| 对比 | 余弦相似度 |
|---|---|
| cos(标题, 标题) | 1.000 |
| **cos(标题, 自己的正文)** | **0.209** |
| cos(标题, 标题+正文) | 0.250 |
| cos(「薄荷的功效」, 标题+正文) | 0.419 |
| cos(「山茱萸的作用」, 标题+正文) | 0.099 |

结论：
1. `paraphrase-multilingual-MiniLM-L12-v2` 对「短查询 ↔ 长文档」的余弦值**被严重压缩**，
   连文档与自身标题都只有 0.25；
2. 因此同领域、句式相似但实体无关的文档（山茱萸、裸柱菊，约 0.65）会压过真正该命中的文档（约 0.50）；
3. 这是**小体量多语模型的固有能力边界**，不是代码缺陷——但必须用工程手段补偿。

## 3. 方案对比（4 组查询，排除后的名次）

| 方案 | 薄荷短查询 | 薄荷标题查询 | 孕妇查询 |
|---|---|---|---|
| A 现状：cos(q, 标题+正文) | 13 | 37 | 1 |
| B 标题/正文分向量取最大 | 25 | **1** | 1 |
| D = B + bigram-IDF 加成 | 13 | **1** | 1 |
| E = B + RRF(向量排名, 词汇排名) | 6 | **1** | 1 |
| F = B + BM25-RRF（等权） | 5 | **1** | 1 |
| G = B + BM25-RRF（词汇权重 2.0） | 3 | **1** | 1 |
| **H = B + BM25-RRF（词汇权重 4.0）** | **1** | **1** | 1（相关文档） |

**采用方案 H**：标题与正文各自成向量、取最大余弦；词汇路用中文 bigram BM25；两路排名用加权 RRF 融合。

## 4. 权重调参（MRR@5，8 条标注查询）

`scripts/tune_retrieval.py` 输出：

| 词汇权重 | MRR@5 | 各查询排名 |
|---|---|---|
| 0.0（纯向量） | 0.875 | 薄荷短查询 >5 ❌ |
| 2.0 | 0.833 | 3 |
| 3.0 | 0.838 | 2 |
| **4.0** | **0.906** | **1** ✅ |
| 6.0 | 0.875 | 1（孕妇查询 >5） |

取 **`TCM_RAG_LEXICAL_WEIGHT=4.0`**（默认值）。

> 说明：标注集中「孕妇用药有哪些禁忌？」的期望文档被记为唯一正确项，但实测 Top3
> 分别是紫苏子（"孕妇…需咨询医生"）、木天蓼（"孕妇…慎用"）、番泻叶（"孕妇便秘"），
> 均为孕妇用药相关的合法文档。即真实相关性优于表格所示指标，此处指标偏保守。

## 5. 工程要点（写入报告可作为「改进点」）

1. **小模型不能只靠向量**：语料是「短查询 → 长答案」形态时，必须补词汇路，
   否则专有名词（薄荷、川乌）会被句式相似度淹没；
2. **标题单独成向量**：Q&A 语料的标题就是问题本身，和用户 query 同构，独立编码收益很大（37 → 1）；
3. **RRF 而非分数相加**：向量余弦（0~1）与 BM25（0~50+）尺度不可比，用排名融合（k=60）天然规避归一化问题；
4. **调参要有标注集**：用 MRR@5 扫权重，避免"修好一个查询、弄坏另一个"；
5. **实现不绑死模型**：`TCM_EMBED_MODEL` 可换更优中文模型（如 BGE 系列），
   混合检索在换模型后依然成立，属于稳健设计。

## 6. 复现命令

```bash
conda activate lora && cd <项目根>
env -u http_proxy -u https_proxy HF_HUB_OFFLINE=1 python scripts/eval_retrieval.py   # 方案对比
env -u http_proxy -u https_proxy HF_HUB_OFFLINE=1 python scripts/tune_retrieval.py   # 权重调参
```

相关配置项：`TCM_RAG_MIN_SCORE=0.20`、`TCM_RAG_LEXICAL_WEIGHT=4.0`、`TCM_RAG_RRF_K=60`。
